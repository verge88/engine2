# engine2

**engine2 v2.5** — экспериментальный игровой runtime и 3D-рендерер на **C++20 / OpenGL 3.3 Core**. Есть glTF 2.0, текстурные PBR-материалы, HDR Image-Based Lighting, несколько точечных источников света, SSAO и отсечение невидимых объектов. Это пока **не полноценный production-движок и не готовый фотореализм**: нет полнофункционального редактора, полноценной физики, аудио и скриптов.

## Возможности

- **Playable demo game — Orb Arena (v2.5):** режим `--game-demo 1` запускает небольшую игру на системах самого движка: синяя физическая сфера собирает 5 Energy Cores внутри замкнутой арены и избегает двух красных Hunter Orbs. WASD управляет игроком, Shift ускоряет, R перезапускает; заголовок окна показывает score/lives/win/game-over. Демо использует обычные `Scene`, Sphere/AABB + Sphere/Sphere contacts, CCD, persistent warm-start, angular velocity/inertia/friction torque, emissive PBR-материалы и стандартный renderer. F1 открывает редактор и ставит игру на паузу. Подробности: `docs/ORB_ARENA.md`.
- **Collision torque и инерция сфер (v2.5):** кулоновское трение теперь решается по скорости **точки контакта** `v + ω×r`. Для динамических сфер используется инерция сплошной сферы `I = 2/5·m·r²`; касательный импульс меняет и COM-скорость, и `angularVelocity`. Это работает для Sphere/Sphere, Sphere/AABB, AABB/Sphere, persistent warm-start, CCD time-of-impact и контакта с ground plane, поэтому скольжение естественно переходит в spin/rolling. Нормальный импульс для сфер torque не создаёт, поскольку плечо параллельно нормали. Вращение AABB/OBB и тензор инерции коробки пока не реализованы.
- **Угловая скорость сфер (v2.5):** динамический `RigidBodyComponent` получил `angularVelocity` в радианах/секунду. Для сфер она интегрирует world-axis вращение визуального transform на каждом fixed step, сохраняя translation и authored scale; состояние сериализуется в Scene JSON, отображается в инспекторе, редактируется JSON-патчем `set-body-angular-velocity` и Dear ImGui. Старые JSON без поля загружаются с нулевым spin. Ненулевая angular velocity для AABB и static body пока отклоняется, потому что текущий box collider остаётся осевым; sphere contact torque и rotational friction уже поддержаны, а OBB/box inertia ещё нет.
- **Persistent contacts / warm starting (v2.5):** resting-контакты между физическими телами теперь сохраняют accumulated normal/tangent impulses между fixed steps и повторно применяют их перед 8 проходами Gauss-Seidel. Кэш привязан к generation-stamped паре сущностей, проверяет совпадение нормали и не используется для нового удара с высокой closing velocity; bounce-импульсы с restitution намеренно не переносятся на следующий шаг. Телепорт, disable/delete и замена RigidBody инвалидируют связанные записи. `--stats` показывает `scenePersistentContacts` и `sceneContactWarmStarts`. Это pair-level warm-start cache, а не multi-point manifold: OBB и полноценные multi-point rotational contacts по-прежнему впереди.
- **CCD динамических AABB (v2.5):** флаг `continuous` теперь работает не только для сфер, но и для translation-only осевых коробок. Событийный CCD использует точный relative-motion sweep: AABB/AABB решается пересечением центра с Minkowski-expanded box, а Sphere/Box сохраняет точную rounded-box геометрию v2.4 для граней, рёбер и углов даже когда движутся оба тела. Поддержаны Box/Box, Box/Sphere и Sphere/Box с несколькими ударами за один fixed step; для moving/moving оба тела должны включить CCD. Вращающиеся OBB и multi-point contact manifolds пока не реализованы.
- GLFW окно, цикл приложения, FPS-камера, управление мышью и клавиатурой.
- **Точное CCD сфер против AABB — грани, рёбра, углы (v2.4):** вместо прежнего пересечения луча с просто расширенной коробкой вычисляется **первый контакт сферы с точным закруглённым объёмом** (Minkowski sum AABB + сфера). Алгоритм аналитически исследует 6 плоских граней, 12 цилиндрических участков рёбер и 8 сферических участков углов; проверяет расстояние до настоящей поверхности, время удара и направление движения. Расчёт квадратных уравнений выполняется в double для устойчивости у углов. Исключаются ложные удары в пустых углах expanded AABB, а настоящие удары получают диагональные нормали, меняющие направление отскока. Весь событийный CCD-цикл v2.3, динамика сфер и трение работают без новых флагов; добавлены `sceneCcdBoxFaceHits`, `sceneCcdBoxEdgeHits`, `sceneCcdBoxCornerHits`. Граница применимости прежняя: **неподвижные осевые коробки**, без вращения, moving-box CCD и устойчивых долговременных contact manifolds.
- **Событийная CCD с несколькими ударами (v2.3):** динамические сферы с `continuous=true` теперь участвуют в едином глобальном временном CCD-цикле: **две движущиеся сферы** с включённой CCD обрабатываются по аналитическому времени пересечения относительных траекторий, а сфера может **несколько раз столкнуться со статическими сферами или AABB-коробками за один шаг 1/60 c**. После каждого удара остаток времени пересчитывается, а swept 3D broadphase перестраивается, поэтому можно отскочить в сторону стены, не лежавшей на исходной траектории. Физика сохраняет массы, restitution и трение на импульсе; максимум **12 CCD-событий на весь мир за один шаг**, при превышении выполняется дискретный fallback с учётом `sceneCcdBudgetExhaustions`. Опциональность сохраняется: `continuous=false` по умолчанию, старые JSON-сцены работают по-прежнему, **обе движущиеся сферы должны включить CCD**. CLI `--collision-demo 1 --ccd 1 --ccd-speed 180` демонстрирует встречный удар, `--box-demo 1` — удар о статическую коробку. Диагностика: `sceneCcdHits`, `sceneCcdDynamicHits`, `sceneCcdBudgetExhaustions`. Всё ещё нет CCD с движущимися коробками, вращательной динамики, точной обработки углов расширенного AABB и гарантии без туннелирования после достижения лимита событий.
- **3D broadphase и ограниченная CCD (v2.2):** поиск потенциальных контактов теперь использует детерминированную **трёхмерную сетку** (ячейки 2 мировые единицы) и swept AABB от начала до конца физического шага. Пары отсеиваются по всем трём координатам, сортируются и исключают дубликаты; особо крупные коллайдеры проходят отдельную fallback-проверку вместо создания миллионов ячеек. Быстрые динамические **сферы** могут включить `continuous` и проверять первый time of impact со **статическими сферами** (точное аналитическое пересечение) и **статическими AABB-коробками** (консервативный swept sphere vs expanded AABB). На столкновении применяется restitution/трение и движение продолжается в оставшейся части шага. `continuous` по умолчанию false, старые JSON-сцены загружаются без CCD. В Dear ImGui есть чекбокс CCD, в CLI-патчах — `set-body-ccd`; демонстрация: `--box-demo 1 --ccd 1 --ccd-speed 180`. `--stats` показывает `sceneBroadphaseCells`, `sceneBroadphaseTests`, `sceneCcdHits`. **Ограничения:** пока обрабатывается максимум один CCD-удар сферы за шаг, нет CCD между двумя движущимися телами, коробочного CCD, вращательной динамики или долгоживущих manifolds.
- **Трение и итерационный решатель контактов (v2.1):** физические тела получили `staticFriction` и `dynamicFriction` (диапазон 0–4, dynamic ≤ static); при контактах применяется кулоновское трение по касательной и накопленные нормальные импульсы. Вместо однократного разрешения пары выполняются **8 последовательных проходов** на каждом фиксированном шаге 1/60 c: это помогает передавать опору через стопки коробок и уменьшать проникновение. Пол с бесконечной массой тоже тормозит скольжение при включённой гравитации. Сила удара/отскок по-прежнему определяется restitution; малые скорости покоя не вызывают постоянных отскоков. **По умолчанию оба коэффициента трения равны нулю**, поэтому старые сцены остаются без трения. Значения записываются в SceneIO JSON v1 (необязательные поля при загрузке), редактируются в Dear ImGui и JSON-патчем `set-body-friction`. `--stats` выводит `sceneSolverPasses`. Пока это ограниченный трансляционный solver: нет угловой динамики/моментов инерции, полного CCD, 3D spatial grid или точного OBB.
- **BVH-ускорение выбора объектов (v2.0):** для каждого `Mesh` один раз при загрузке строится и хранится бинарное дерево Bounding Volume Hierarchy по центроидам треугольников (median split, лист до 8 примитивов). CPU-луч сначала проходит AABB всего меша, а затем посещает **только пересечённые узлы BVH**, проверяя реальные треугольники внутри листьев. Дочерние узлы обходятся от ближнего к дальнему с отсечением по уже найденному hit distance. Работает с glTF, процедурными мешами, масштабом и иерархией. BVH переносится вместе с Mesh при move-конструкции/присваивании и не пересчитывается каждый кадр. Режим `--pick-geometry bounds` сохранён. `--stats` сообщает `pickBVHNodes` и `pickTriangles` для последнего луча; те же счётчики видны в Dear ImGui. Тест на 32 768 треугольниках требует минимум **50-кратного уменьшения числа triangle intersection checks** относительно полного перебора — не обещание 50× FPS или времени кадра. Плата за ускорение — дополнительная CPU-память под BVH и время его построения.
- **Точный выбор по треугольникам и выделение прямоугольником (v1.9):** после быстрого AABB-отсечения CPU-луч проверяет **реальные треугольники Mesh** двухсторонним тестом Мёллера—Трумбора и выбирает ближайшую геометрическую поверхность даже у повёрнутого и неравномерно масштабированного объекта. Для этого Mesh сохраняет CPU-копию позиций и индексов (дополнительная память). Выбор мышью через пустое место можно превратить в **marquee** — потянуть прямоугольник вокруг объектов; Ctrl/Shift добавляет найденные сущности к группе без дублирования. Прямоугольник пересекает проекции габаритов мешей, не проверяет точные треугольники или видимость за другими объектами. CLI: `--pick-geometry triangles|bounds`, `--marquee-screen X0 Y0 X1 Y1`, `--marquee-add X0 Y0 X1 Y1`. Режимы рендера и сцены v1.8 сохранены.
- **Выбор объектов из 3D-окна и множественное выделение (v1.8):** щелчок по видимому мешу строит луч камеры и выбирает ближайшую сущность по пересечению с её трансформированным локальным AABB; поддерживаются повёрнутые/масштабированные меши, glTF и parent-child иерархии. **Ctrl/Shift+click** добавляет или снимает объекты в выделении. Несколько выбранных объектов получают цветные экранные рамки и редактируются одним жестом 3D-гизмо/Undo; выбранные родители исключают двойное преобразование дочерних сущностей. Кнопка Delete удаляет группу одной операцией. Для автоматизации: `--pick-screen X Y`, `--pick-add X Y`, `--gui-add entity-index`; статистика `guiSelectedCount` / `guiSelectedIndex`. Ray picking использует AABB геометрии, а не треугольники или GPU ID buffer.
- **Редактор 3D-трансформаций (v1.7):** 3 режима манипулятора в Dear ImGui: **Move** (перемещение по мировым осям X/Y/Z), **Rotate** (проецируемые 3D-кольца вокруг мировых осей), **Scale** (локальное масштабирование вдоль осей с сохранением позиции). Кнопки выбора режима и настройка **Snap** (шаг перемещения по мировой сетке, 15° и множитель масштаба 0.25). CLI: `--gizmo-mode move|rotate|scale`, `--gizmo-snap 0|1`, `--gizmo-grid 0.05..20`. Преобразования отсчитываются от состояния объекта до начала перетаскивания, поэтому snapping устойчив, а Undo отменяет весь жест целиком. Поддерживаются масштабированные и повёрнутые родительские объекты, но при неоднородном масштабе родителей вращение может создавать shearing в локальной матрице.
- **3D-гизмо и Undo/Redo (v1.6):** цветные оси X/Y/Z рисуются поверх сцены у выбранной сущности. Их можно перетаскивать мышью для перемещения объекта по **мировой оси**; изменение переводится обратно в локальную матрицу с учётом родителя и сохраняет поворот и масштаб. `--gizmo 0|1` (по умолчанию 1) позволяет скрыть манипулятор. Кнопки Undo/Redo и Ctrl+Z/Ctrl+Y/Ctrl+Shift+Z восстанавливают целиком состояние сцены: дерево, материалы, свет, компоненты и удалённые сущности. История ограничена 64 снимками, одно непрерывное перетаскивание = один шаг отмены. При переключении GUI физика и камера приостанавливаются, история не сохраняется в JSON.
- **Графический редактор Scene (v1.5):** в окно OpenGL 3.3 интегрирован Dear ImGui (GLFW + OpenGL3, фиксированная версия v1.91.9b). Панель показывает настоящее дерево иерархии, дочерние объекты, количество компонентов, выбранную сущность и её свойства. Можно создать/удалить сущность, изменить имя, enabled, локальное положение, parent с сохранением мировой позиции, PBR albedo/metallic/roughness, интенсивность/диапазон/цвет света, velocity/mass/restitution/gravity/static физического тела. Кнопка сохраняет весь мир в JSON через существующий SceneIO. F1 переключает GUI и мышь; при открытой панели камера и физика приостанавливаются. Для интерактивного запуска панель включена по умолчанию; при `--frames` выключена для сохранения старых image regression тестов, принудительно `--gui 1`. `--gui-select N` выбирает сущность для воспроизводимого тестирования.
- **CLI-инспектор и пакетный редактор Scene (v1.4):** `--inspect-scene report.json` экспортирует список сущностей, индекс/parent/depth, локальные и мировые координаты, эффективную видимость и значения компонентов. `--edit-scene edits.json` применяет атомарный JSON-патч к загруженной или созданной сцене: rename, set-enabled, set-position (local/world), reparent с keepWorld, set-albedo, set-light-intensity, set-body-velocity и delete. Все индексы относятся к одной исходной записи в `Scene::entities()`. При неверной операции весь набор отменяется. Это **не графический редактор**.
- **JSON-сцены (v1.2):** версионированный формат `engine2.scene` v1 сохраняет живые сущности, имена, enabled, локальные матрицы и parent-child связи, `MeshRenderer` со всеми основными полями PBR-материала и ссылками на текстуры, `PointLight`, `RigidBody` с текущими скоростями, массами и другими параметрами. Меши и GPU-текстуры сохраняются по стабильным ключам ресурсов вместо указателей и OpenGL ID. Двухпроходная загрузка проверяет родителей, циклы, версии и отсутствие ресурсов. CLI: `--save-scene` / `--load-scene`.
- **Scene runtime (v1.0):** сущности с generation handles (защита от stale references), произвольные имена, дочерние объекты и локальные/world трансформации, проверки циклов, переподчинение с сохранением world matrix, рекурсивное удаление, отключение видимости родительских объектов. Компоненты `MeshRenderer`, `PointLight`, `RigidBody`. Рендерер и точечные источники получают данные из Scene, включая при загрузке glTF.
- **Фиксированный игровой шаг:** обновление физических тел на 60 Гц с аккумулятором времени и максимум 8 шагами на кадр. Поддержаны гравитация и столкновение сферы с горизонтальной плоскостью.
- **Коробчатые коллайдеры (v1.3):** AABB в мировых единицах через `ColliderShape::Box` и `halfExtents`. Неподвижные и динамические коробки сталкиваются со сферами и друг с другом, сохраняют mass/restitution импульсы и X sweep-and-prune. Обработка удара об грань, угол, пересечения центра сферы с внутренностью коробки. Новая процедурная геометрия `Mesh::cube()`, `--box-demo 1` и статистика `sceneBoxContacts`. JSON `engine2.scene` v1 теперь сохраняет `shape` и `halfExtents`, при этом читает старые сцены без этих полей как сферы.
- **Физические столкновения сфер (v1.1):** sweep-and-prune broadphase по X, отсечение непересекающихся осей Y/Z, sphere-sphere narrowphase, коррекция взаимного проникновения и импульсы отскока с учётом `mass` и `restitution`. Компонент `isStatic` задаёт неподвижный коллайдер с бесконечной массой. Счётчики `sceneBroadphasePairs` и `sceneSphereContacts` отражают обработанные пары и контакты за время симуляции. При совпадении центров используется предсказуемое направление разделения.
- Индексированные меши, процедурная геометрия, трансформации, локальные AABB.
- Импорт **glTF 2.0 (.gltf/.glb)**: меши, UV0, иерархия узлов, инстансы, генерация нормалей и тангентов.
- Текстурные PBR-материалы: base color (sRGB), metallic/roughness, normal, AO, emissive.
- **glTF alpha modes:** `OPAQUE`, `MASK` (порог отсечения и текстурный alpha-канал в PBR, shadow map и SSAO) и `BLEND` (depth test + сортировка мешей по расстоянию + смешивание цветов в линейном HDR-буфере). Прозрачные объекты рисуются после непрозрачных; `MASK` сохраняет глубину и отбрасывает непрозрачные тени по силуэту.
- **Cook–Torrance GGX**: направленный солнечный свет с **3 каскадами PCF-теней**, до 8 движущихся точечных источников с обратноквадратичным затуханием.
- **Каскадные тени от солнца (v0.7):** 0, 1 или 3 каскада из глубинного OpenGL 3.3 texture-array (1536×1536 на слой). Схема разделения глубины 60% logarithmic / 40% linear, привязка к сетке текселей, отдельное отбрасывание shadow casters и 3×3 PCF. Дальность солнечных теней настраивается независимо от дальности камеры. `--cascade-debug 1` визуально помечает каскады.
- **Точечные тени (v0.6):** до **2** из этих источников создают собственные **кубические карты глубины** с 6 направлениями каждая (256×256 на грань), радиальным сравнением расстояний и 12-tap PCF. Маскированные glTF-материалы отбрасывают тени по alpha-cutoff; BLEND не отбрасывают тени.
- **HDR IBL**: панорама Radiance `.hdr` или процедурный небосвод, diffuse irradiance, GGX specular prefilter, split-sum BRDF LUT.
- **Temporal Anti-Aliasing (v0.8):** 8-точечный Halton(2,3) jitter камеры, HDR history ping-pong в 16-битном float, восстановление мировых координат по depth texture и reprojection предыдущей view-projection матрицей. Depth-disocclusion rejection и ограничение исторического цвета по 3×3 окрестности уменьшают шлейфы. Фильтрация выполняется до bloom и ACES. Каскадные карты солнечных теней вычисляются по **недрожащей** матрице камеры; при изменении разрешения, переключении TAA и резком перемещении история сбрасывается.
- **SSAO**: полурезолюционный геометрический проход (позиция/нормаль в координатах камеры), 16 hemisphere samples и edge-aware blur; влияет на непрямое освещение, а не на прямой свет.
- **Frustum culling**: шесть плоскостей камеры проверяются против трансформированных AABB; shadow casters проверяются отдельно во фрустуме каждого каскада солнца, чтобы не терять тени от объектов вне кадра.
- **Автоматическая HDR-экспозиция (v0.9):** выделенный GPU-проход 128×128 вычисляет логарифм яркости, а цепочка mipmap усредняет его до 1×1. CPU адаптирует экспозицию экспоненциально с учётом реального `deltaTime` (в среднем по геометрической яркости). Параметры `--auto-exposure`, `--exposure-key`, `--exposure-speed`; прежний `--exposure` остаётся ручной экспокоррекцией (множителем).
- **Многоуровневый bloom (v0.9):** пять отдельных HDR RGBA16F буферов 1/2—1/32 размера, soft-knee threshold, 13-tap downsample и аддитивный tent upsample. Яркость и порог настраиваются отдельно: `--bloom` и `--bloom-threshold`.
- HDR framebuffer RGBA16F, TAA-resolved HDR перед bloom/тональной компрессией, ACES tonemapping.
- PPM-screenshot, диагностические счётчики draw calls, CTest с базовыми проверками пикселей и математики.

Внешние зависимости: GLFW, glad, GLM, tinygltf/stb. Код GPU-проходов, фильтров, PBR-шейдеров, отбраковки и приложения находится в `engine2`.

## Точная геометрия CCD на гранях, рёбрах и углах (v2.4)

```bash
# Стандартный CCD-сценарий: сфера сталкивается со статической коробкой
./build/engine2 --box-demo 1 --ccd 1 --ccd-speed 180 \
  --frames 1 --sim-dt 0.0166667 --stats

# Численные тесты новой геометрии и интеграции со сценой
ctest --test-dir build -R 'ccd-rounded-box' --output-on-failure
```

Раньше расширение AABB на радиус сферы давало только **консервативное** пересечение: луч мог пройти по пустому углу и при этом пересечь увеличенную коробку. Теперь рассматривается поверхность `AABB ⊕ sphere(radius)` — плоские грани, цилиндры вокруг рёбер и сферы вокруг углов. CCD выбирает ближайшую допустимую точку первого контакта; нормаль к цилиндру или сферическому углу вычисляется из настоящей геометрии, а не по одной оси. Это влияет и на момент удара, и на остаточное движение в том же fixed step.

Счётчики в `--stats`: `sceneCcdBoxFaceHits`, `sceneCcdBoxEdgeHits`, `sceneCcdBoxCornerHits`. Они учитывают **CCD-удары** по геометрическим элементам статических коробок, а не дискретные penetration contacts. Unit-тест сравнивает 361 осевую траекторию с независимой формулой времени касания; интеграционные и Xvfb/OpenGL-тесты проверяют отскок по диагональной нормали и отсутствие ложного удара в пустом углу.

**Ограничение:** точный sweep относится только к динамической сфере и **неподвижному, axis-aligned box collider**; вращающиеся коробки, движущиеся box colliders, capsule/mesh CCD и долгоживущие контактные manifolds остаются будущими задачами. Непрерывные удары по-прежнему ограничены 12 событиями на fixed step.

## Несколько CCD-ударов и столкновения движущихся сфер (v2.3)

```bash
# Две быстрые сферы проходят сквозь друг друга в дискретном режиме:
./build/engine2 --collision-demo 1 --ccd 0 --ccd-speed 180 \
  --frames 1 --sim-dt 0.0166667 --stats --screenshot discrete.ppm

# С CCD сферы встречаются и отражаются (sceneCcdDynamicHits=1):
./build/engine2 --collision-demo 1 --ccd 1 --ccd-speed 180 \
  --frames 1 --sim-dt 0.0166667 --stats --screenshot continuous.ppm

# Запустить численные тесты относительного TOI и цепочек столкновений:
ctest --test-dir build -R 'ccd-moving-spheres-math|ccd-multi-impact-scene' \
  --output-on-failure
```

Флаг `RigidBodyComponent.continuous` включает CCD **индивидуально** для динамических сфер. Между двумя движущимися сферами CCD включается только при `continuous=true` **у обеих**; иначе контакты остаются дискретными. После каждого непрерывного удара движок сдвигает участников к моменту контакта, применяет нормальный и касательный импульсы и перестраивает 3D broadphase для оставшегося времени шага. Это позволяет корректно обработать несколько отскоков между неподвижными стенами или передачу импульса по цепочке сфер. Динамические коробки остаются в дискретном решателе.

На один фиксированный шаг установлен глобальный предел **12 CCD-ударов** во избежание бесконечной обработки тесных контактов. Превышение отражается в `sceneCcdBudgetExhaustions`; остаточное время интегрируется без непрерывного поиска. `sceneCcdDynamicHits` учитывает удары между двумя движущимися сферами, `sceneCcdHits` — все непрерывные удары. Точность статических AABB около углов остаётся консервативной; полноценные persistent manifolds, CCD динамической коробки и вращательная физика ещё не реализованы.

## Пространственный broadphase и CCD для быстрых сфер (v2.2)

```bash
# Сфера движется на 180 единиц/с и за один шаг пересекает препятствие:
# без CCD она проходит насквозь; с CCD отражается от статической коробки
./build/engine2 --box-demo 1 --ccd 0 --ccd-speed 180 \
  --frames 1 --sim-dt 0.0166667 --stats --screenshot no-ccd.ppm

./build/engine2 --box-demo 1 --ccd 1 --ccd-speed 180 \
  --frames 1 --sim-dt 0.0166667 --stats --screenshot with-ccd.ppm

# Только CPU-тесты broadphase / CCD (без OpenGL)
ctest --test-dir build -R 'physics-3d-broadphase-ccd-.*-unit' -V
```

Включение CCD поддерживается на уровне `RigidBodyComponent.continuous = true` (или чекбокс **CCD (sphere vs static)** в инспекторе сущности). Для JSON-сцены `engine2.scene` v1 добавлено необязательное булево поле `continuous`; старые сохранения по умолчанию загружаются в дискретном режиме. В пакетном редакторе доступна операция `{"op":"set-body-ccd","entity":27,"continuous":true}`. Параметры `--ccd 0|1` и `--ccd-speed 0..10000` действуют **только вместе с** `--box-demo 1` и на демонстрационную сферу.

3D broadphase использует world-space swept bounds, включая скорость объекта за весь шаг, поэтому быстрый снаряд не исчезает из кандидатов между стартом и концом траектории. Тест на 300 телах с совпадающим X, но разнесёнными Y/Z, не создаёт ни одной кандидатной пары; пересечения и дедупликация сверены с полным перебором. CCD по статической сфере вычисляет аналитический TOI, для AABB использует расширенную коробку, что **может преждевременно сработать на углах**. Отслеживается только первый CCD-удар на каждом шаге: отскок в следующую стену внутри того же шага пока не решается непрерывно. Остальные тела по-прежнему обслуживаются 8-проходным дискретным решателем с трением.

## Трение и устойчивые контакты (v2.1)

```bash
# Демонстрация столкновения сферы и коробки со скольжением
./build/engine2 --box-demo 1 --lights 0 \
  --edit-scene tests/data/scene-friction-demo.json \
  --frames 40 --sim-dt 0.0166667 --stats

# Выгрузить состояние мира после симуляции, включая коэффициенты трения
./build/engine2 --box-demo 1 --lights 0 \
  --edit-scene tests/data/scene-friction-demo.json \
  --frames 40 --sim-dt 0.0166667 \
  --save-scene friction-world.json

# Проверить физические unit-тесты
ctest --test-dir build -R 'contact-solver-friction|scene-friction-stacking' -V
```

В `RigidBodyComponent` доступны два независимых коэффициента: `staticFriction` удерживает тело от начала скольжения, `dynamicFriction` сопротивляется уже начавшемуся скольжению. Допустимый диапазон — 0–4 с `dynamicFriction` не выше `staticFriction`. По умолчанию оба 0. Для пар тел коэффициенты комбинируются геометрическим средним; для земли используется коэффициент самого тела. Все значения сериализуются как необязательные поля в текущем `engine2.scene` JSON v1: более старые сохранения без новых ключей загружаются с нулевым трением. В JSON-патчах операции `{"op":"set-body-friction","entity":27,"staticFriction":2.0,"dynamicFriction":1.5}` применяются транзакционно.

Разрешение столкновений теперь выполняет 8 итераций по сохранённым кандидатным парам на каждом шаге симуляции. Метод приближённый (sequential impulses + коррекция проникновения); он улучшает поддержку стопок, но не гарантирует устойчивость всех сложных конфигураций. Столкновения по-прежнему поддерживают sphere/sphere, sphere/AABB и AABB/AABB без вращательной физики. Число `sceneSolverPasses` в `--stats` — накопленные проходы решателя, а не число контактов или миллисекунд CPU.

## BVH: ускоренный ray picking (v2.0)

```bash
# BVH — стандартный режим точного выбора по треугольникам
./build/engine2 --gui 1 --pick-geometry triangles \
  --pick-screen 640 467 --frames 2 --stats

# Для сравнения — режим только ограничивающих AABB
./build/engine2 --gui 1 --pick-geometry bounds \
  --pick-screen 640 467 --frames 2 --stats

# Численный CTest/benchmark: 32,768 треугольников и 49 лучей
ctest --test-dir build -R triangle-bvh-acceleration-unit \
  --output-on-failure -V
```

В статистике `pickTriangles` — реальное число выполненных тестов на треугольник для последнего вызова screen ray-pick, а `pickBVHNodes` — количество посещённых узлов дерева по всем кандидатным мешам. При `--pick-geometry bounds` оба счётчика равны нулю, потому что точная геометрия не просматривается. Цель ускорения — уменьшить число тестов на больших glTF-мешах, но эффективность зависит от пространственного распределения треугольников: если центроиды совпадают, дерево не может эффективно разбить геометрию. Для skinned/animated/deforming mesh потребуется отдельное обновление BVH; v2.0 строит его только для **статической локальной геометрии**, а движения сущностей учитывает преобразованием луча.

## Точное ray picking и рамка выделения (v1.9)

```bash
# Точные пересечения с треугольниками — режим по умолчанию
./build/engine2 --gui 1 --pick-geometry triangles

# Для диагностики старого режима выбора по ограничивающим коробкам
./build/engine2 --gui 1 --pick-geometry bounds

# Рамка выделения из пикселей экрана (x0,y0) -> (x1,y1)
./build/engine2 --gui 1 --marquee-screen 600 440 690 505 \
  --frames 2 --stats --screenshot selected.ppm

# Дополнить текущее выделение, а не заменить его
./build/engine2 --gui 1 --gui-select 13 \
  --marquee-add 600 440 690 505 --frames 2 --stats

# Тест границ: этот луч проходит внутри AABB, но мимо треугольника
./build/engine2 --model tests/data/triangle-picking-gap.gltf \
  --gui 1 --pick-screen 700 325 --frames 2 --stats
```

**В редакторе:** щёлкни по видимому мешу для точного выбора его треугольников; удерживай Ctrl/Shift для переключения одного объекта. Чтобы выбрать группу, начни перетаскивание **на пустом участке 3D-вида**: появится прозрачный синий прямоугольник. Отпускание кнопки выделяет все сущности, чьи проекции bounding boxes пересекают область; удерживай Ctrl/Shift при начале, чтобы дополнить существующее выделение. Рамка и единичный выбор используют разные уровни геометрической точности. Движение уже выбранного объекта через X/Y/Z gizmo по-прежнему имеет приоритет над выбором.

В отличие от v1.8, луч больше не выбирает «воздух» в пустых областях внутри AABB меша. Результат **не учитывает прозрачные пиксели альфа-текстуры, skinning и морфинг**, а CPU-обход треугольников пока линейный после AABB-отсева. Для больших мешей понадобится BVH или GPU ID-buffer. Рамка — консервативная, по габаритам, может захватывать полностью скрытые/перекрытые объекты. Полный экран прямоугольника может выбрать и пол; это ожидаемо.

## Выделение объектов из 3D-окна и группы (v1.8)

```bash
# Нажимай ЛКМ на меше непосредственно в 3D-сцене;
# Ctrl/Shift + ЛКМ добавляет или убирает объект из выделения
./build/engine2 --gui 1

# Воспроизводимый выбор сферы №23 лучом из пикселя (640,467)
./build/engine2 --gui 1 --pick-screen 640 467 --frames 2 --stats

# Добавить соседнюю сферу №24: теперь выделены оба объекта
./build/engine2 --gui 1 --pick-screen 640 467 --pick-add 758 467 \
  --frames 2 --stats --screenshot multiselection.ppm

# Выбрать объекты напрямую по индексам без screen ray
./build/engine2 --gui 1 --gui-select 23 --gui-add 24
```

При обычном щелчке текущее выделение заменяется; **Ctrl** или **Shift** переключают отдельную сущность. Щелчок по свободному месту снимает выделение (в режиме добавления сохраняет текущие объекты). В списке иерархии действует то же поведение, что в 3D-виде. Последний выбранный объект считается **основным**: его свойства показывает инспектор, и вокруг него расположены ручки гизмо. Цветные рамки показывают остальных членов группы. Гизмо применяется к корневым выбранным сущностям, поэтому если выделен родитель и ребёнок, потомок не сдвигается дважды. Вращение/масштаб группы выполняется вокруг центра **каждого** выбранного объекта, а не вокруг общего pivot; Undo отменяет групповой жест целиком.

**v1.9:** луч выбирает реальные треугольники (по умолчанию); альтернативный старый AABB-алгоритм доступен через `--pick-geometry bounds`. Рамка выбирает объекты по перекрытию проекций AABB без точного пересечения треугольников, не проверяет окклюзию и прозрачность. Выделение треугольников как отдельных редактируемых подобъектов пока не предусмотрено.

## 3D-манипуляторы: перемещение, вращение и масштаб (v1.7)

```bash
# Интерактивное редактирование с 3D-кольцами вращения
./build/engine2 --gui 1 --gui-select 13 --gizmo-mode rotate

# Масштаб объекта вдоль его локальной оси (квадратные ручки)
./build/engine2 --gui 1 --gui-select 13 --gizmo-mode scale

# Перемещение с привязкой к мировой сетке 0.5 единицы
./build/engine2 --gui 1 --gui-select 13 --gizmo-mode move \
  --gizmo-snap 1 --gizmo-grid 0.5

# Сравнение снимков разных режимов
./build/engine2 --gui 1 --gui-select 13 --gizmo-mode rotate \
  --frames 2 --screenshot rotate.ppm
```

В панели Scene Editor выбери **Move**, **Rotate** или **Scale**. Для Move и Scale по-прежнему используются красная X, зелёная Y и синяя Z оси: круглый наконечник означает перемещение, квадратный — масштаб. В режиме Rotate вокруг выбранного объекта проецируются три мировых кольца; нажми и перетаскивай видимый участок кольца, чтобы вращать объект вокруг его центра. Вращение отслеживает угловое движение мыши на экране; при сильном перспективном искажении это приближение, а не полноценный CAD-манипулятор.

Флажок **Snap** включает округление мировой позиции к сетке с редактируемым шагом, угла — с шагом **15°**, коэффициента масштаба — с шагом **0,25**. Для масштабирования исходный local transform сохраняет позицию и ориентацию объекта. Для вращения применяется world-axis rotation, затем пересчитывается local matrix через обратную матрицу родителя. Не допускается редактирование мировых осей под сингулярной parent-матрицей. У каждого непрерывного жеста один шаг истории — **Undo (Ctrl+Z)** / **Redo (Ctrl+Y)**, также **Ctrl+Shift+Z**. История ограничена 64 снимками и не сохраняется в JSON.

## Встроенный графический инспектор сцены (Dear ImGui)

```bash
# В обычном интерактивном режиме ImGui открыт автоматически
./build/engine2

# Во время работы F1 закрывает/открывает редактор и переключает курсор
# Детерминированная демонстрация с выбранной сущностью №13
./build/engine2 --gui 1 --gui-select 13 --frames 2 \
  --lights 0 --screenshot gui.png.ppm

# Выполнить прежние графические тесты без панели
./build/engine2 --gui 0 --frames 2
```

Слева находится список сущностей с их реальными parent-child связями. После выбора доступны редактирование имени (Enter подтверждает), локального положения, enabled, родителя, PBR-материала, источника света и параметров RigidBody. Кнопка **Save scene JSON** записывает сцену в указанное поле пути (по умолчанию `scene-edited.json`), результат можно затем загрузить через `--load-scene`. Для безопасности и удобства редактирования во время открытой панели камера/физика и анимированные демонстрационные источники света приостановлены, а когда F1 закрывает панель — симуляция возобновляется.

Это встраиваемый runtime-инспектор, пока **не отдельный полноценный редактор**: есть undo/redo и gizmo перемещения, но пока нет asset browser, вращения/масштабирования во viewport или полноценного инструментария отдельного редактора. CLI-инспектор и пакетные JSON-правки версии 1.4 сохраняются независимо от GUI.

## Инспектор и редактор игровых сущностей (CLI)

```bash
# Получить JSON-отчёт: список entities с индексами, hierarchy и компонентами
./build/engine2 --lights 0 --sim-dt 0 --frames 1 \
  --inspect-scene report.json

# Отредактировать исходную сцену тестовым JSON-патчем, сохранить результат
./build/engine2 --lights 0 --sim-dt 0 --frames 1 \
  --edit-scene tests/data/scene-edits-demo.json \
  --inspect-scene edited-report.json --save-scene edited-scene.json

# Повторно открыть изменённый мир, не сдвигая физику
./build/engine2 --load-scene edited-scene.json --sim-dt 0 \
  --frames 1 --inspect-scene restored-report.json
```

Формат файла изменений (значение `entity` — индекс элемента из `entities` в отчёте или из массива `Scene::entities()`):

```json
{
  "format": "engine2.scene-edits",
  "version": 1,
  "operations": [
    {"op": "rename", "entity": 13, "name": "Green Sphere"},
    {"op": "set-position", "entity": 13, "space": "world",
     "position": [0, 1.4, 0]},
    {"op": "set-albedo", "entity": 13, "color": [0.05, 0.95, 0.15]},
    {"op": "set-enabled", "entity": 14, "enabled": false}
  ]
}
```

Другие операции: `reparent` с `parent` (индекс/null) и `keepWorld` (по умолчанию true), `set-light-intensity` с `intensity`, `set-body-velocity` с `velocity` и `delete`. Переподчинение физического объекта не допускается. Все ссылки `entity` в одном патче относятся к **исходным индексам до выполнения операций**, а при ошибке ни одна операция не применяется. Для сохранения изменений необходим `--save-scene`. Анимированные демонстрационные огни не перезаписывают изменения, внесённые через `--edit-scene`.

C++ API: `include/engine2/SceneInspector.hpp`, `inspectScene`, `saveSceneInspection`, `applySceneEdits`, `applySceneEditsFile`.

## Сохранение и загрузка игровых сцен (JSON)

```bash
# Сохранить состояние мира ПОСЛЕ 12 физических кадров
./build/engine2 --collision-demo 1 --sim-dt 0.05 --lights 0 \
  --frames 12 --save-scene scene.json --screenshot before.ppm

# Загрузить те же MeshRenderer, трансформации, компоненты и скорости
# --sim-dt 0 фиксирует физику для сравнения с последним кадром
./build/engine2 --load-scene scene.json --lights 0 --sim-dt 0 \
  --frames 1 --screenshot after.ppm

# Сохранить сцену glTF, включая ссылки на текстуры и alpha MASK/BLEND
./build/engine2 --model tests/data/alpha-mask.gltf --lights 0 \
  --frames 1 --save-scene imported.json
./build/engine2 --model tests/data/alpha-mask.gltf --load-scene imported.json \
  --frames 1
```

Файл не содержит самих геометрических и текстурных данных: для восстановления glTF нужно заново указать **ту же** исходную модель через `--model`. Для процедурных `sphere` и `floor` ссылки разрешаются автоматически. При `--load-scene` сцена из файла **заменяет** сцену по умолчанию; `--lights` не перезаписывает сохранённые светильники, а `--physics-demo` / `--collision-demo` с загрузкой несовместимы.

C++ API: `include/engine2/SceneIO.hpp`, `SceneAssetRegistry`, `serializeScene`, `deserializeScene`, `saveScene`, `loadScene`. Для инспектора доступны `Scene::entities()` и константные указатели на компоненты.

## Параметры

```bash
# Включённый по умолчанию SSAO и 3 движущихся локальных источника
./build/engine2

# Внешние модель и окружение, 6 цветных огней
./build/engine2 --model assets/scene.glb --environment assets/studio.hdr --lights 6 --point-shadows 2

# Отключить затенение окружения или все точечные источники
./build/engine2 --ssao 0 --lights 0

# Сохранить подсветку, но отключить тени точечных источников
./build/engine2 --lights 3 --point-shadows 0

# Детерминированная проверка разных настроек теней (время анимации = 0)
./build/engine2 --lights 1 --point-shadows 1 --light-time 0 --frames 2 --stats

# Каскады солнечных теней, дистанция и режим отладки (цветные зоны)
./build/engine2 --sun-cascades 3 --sun-distance 95 --cascade-debug 1

# Сравнение с одиночной картой или полностью без солнечных теней
./build/engine2 --sun-cascades 1
./build/engine2 --sun-cascades 0

# Сравнить TAA с выключенным сглаживанием
./build/engine2 --taa 1 --taa-weight 0.9
./build/engine2 --taa 0

# Отключить frustum culling для отладки геометрии
./build/engine2 --culling 0

# Автоэкспозиция включена по умолчанию; можно настроить среднюю
# целевую яркость и скорость адаптации или включить полностью ручной режим
./build/engine2 --auto-exposure 1 --exposure-key 0.18 --exposure-speed 1.5
./build/engine2 --auto-exposure 0 --exposure 0.85

# Многоуровневый bloom и мягкий порог выделения ярких областей
./build/engine2 --bloom 0.3 --bloom-threshold 1.2

# Экспозиция, bloom, статистика и сохранение PPM
./build/engine2 --exposure 0.75 --bloom 0.25 --frames 2 --stats --screenshot frame.ppm

# Автоматические тесты
ctest --test-dir build --output-on-failure
```

## Ограничения версии 2.4

- **Scene JSON — данные сущностей, а не самодостаточный asset-bundle:** меши и текстуры должны существовать в `SceneAssetRegistry` при загрузке; для glTF необходимо передавать ту же модель через `--model`. GPU ID, версии entity handle, внутренний накопитель/счётчики физики, настройка камеры и другие runtime-состояния не сохраняются. Вектор скорости и параметры коллайдера сохраняются. Нет миграции между версиями схемы, delta-save, autosave или визуального редактора. Недоступные asset keys или некорректные/циклические parent-связи приводят к ошибке вместо молчаливой подмены ресурсов.
- **Scene — компактная компонентная система, а не archetype ECS:** нет отдельного редактора с asset-browser, системы скриптов, параллельного update, поисковых запросов по компонентам или полноценных игровых событий. Иерархия glTF в runtime пока импортируется как готовые world-матрицы отдельных primitives; исходные parent-child связи glTF не восстанавливаются.
- **Графический редактор v2.0** теперь использует BVH для точных треугольников для одиночного ray picking и AABB-проекции для прямоугольника. Нет учёта альфа-текстур и GPU ID-buffer, окклюзии в marquee, полноценного общего pivot для группового поворота/масштаба, произвольного local-axis rotation/scale snapping, asset browser, скриптов, hot reload или отдельного editor-приложения. Режим Rotate использует приближённый отклик экранного угла мыши; при очень косом обзоре колец удобство ограничено. Масштаб работает по локальным осям, вращение — по мировым. Snapshot-история занимает оперативную память и не сериализуется; Undo/Redo не откатывают физические кадры, прошедшие при закрытом редакторе. Выбор сущности хранится по generation-stamped handle. `--gui 1` показывает панель даже при `--frames`; без явного переключателя автоматические скриншоты остаются без GUI.
- **Редактор v1.4 работает через CLI и JSON-файлы**, и остаётся доступен наряду с GUI. Индексы сущностей действуют в пределах одной сцены и одного набора правок; после удаления/пересоздания они могут измениться. Не реализованы undo/redo, viewport gizmos, live hot-reload, скрипты и сохранение camera/renderer settings в файле сцены. Правки выполняются перед рендерингом, а инспекция в CLI — при завершении запуска.
- **Физика v2.4 — улучшенный прототип:** sphere/AABB, 3D spatial broadphase, кулоновское трение, 8 итераций дискретного solver и до 12 CCD-событий за fixed step. Непрерывные удары работают между двумя opt-in динамическими сферами и между сферой и неподвижной сферой/осевой коробкой. CCD для статической AABB теперь учитывает **точную геометрию граней, рёбер и углов**. **CCD динамических коробок отсутствует**, а по умолчанию continuous выключен. Лимит CCD событий может приводить к туннелированию после его исчерпания. Не реализованы вращательная динамика, joints, capsule/mesh colliders или persistent manifolds. Коллайдеры должны быть корневыми, не вращаются и имеют размеры в мировых единицах. Сильное проникновение и остаточная нестабильность нескольких контактов возможны; не более 8 фиксированных шагов на кадр.
- **Тени только от первых 0–2 точечных источников:** остальные точечные огни освещают сцену без теней. Дополнительные карты включают 6 проходов на источник; при движении всех огней карты перерисовываются каждый кадр. Тени из PCF остаются приближёнными. Динамическое выделение теневых ресурсов и caching пока отсутствуют.
- SSAO не учитывает normal maps и является экранным приближением, не глобальным освещением; возможно появление артефактов на границах.
- Расчёт IBL основан на статическом HDR-окружении. Нет трассировки лучей, SSR, настоящего GI и motion vectors объектов.
- Импорт glTF ограничен TRIANGLES и UV0 без анимаций, скининга, sparse accessors и extensions.
- Прозрачные glTF `BLEND`-поверхности отсортированы **по центру меша**, поэтому пересекающиеся треугольники внутри мешей, сложные слои и самопересечения могут отображаться некорректно (order-independent transparency пока нет). `BLEND` не пишет глубину, не отбрасывает тени и не участвует в SSAO; `MASK` учитывается всеми тремя проходами. Материалы без `MASK`/`BLEND` остаются полностью непрозрачными.
- Frustum culling CPU не использует иерархические деревья/батчинг: одна проверка на экземпляр. Статистика считает только переданные в API `RenderItem` и draw calls из shadow/PBR-проходов.
- **Текущая автоэкспозиция считывает одну 1×1 R16F mip-точку с GPU на CPU каждый кадр:** это простая реализация с возможной синхронизацией CPU/GPU. Для больших игр потребуется асинхронное чтение (PBO/fence) или полностью GPU-resident экспозиция. При резкой смене освещения адаптация намеренно плавная.
- Многоуровневый bloom выполняет несколько полноэкранных проходов; число слоёв фиксировано (5), нет dirt mask, lens flare и physically based glare.
- **TAA использует репроекцию только от движения камеры, без motion vectors объектов.** Анимированная геометрия, прозрачные поверхности, быстро движущиеся источники света и резкие изменения shading могут оставлять артефакты/ghosting. У неба пока нет отдельной исторической репроекции, поэтому TAA для него пропускается. Это не полная реализация TAA уровня крупного игрового движка.
- Три солнечных каскада обновляются каждый кадр: это до трёх полноразмерных проходов теней. На расстояниях дальше `--sun-distance` тени от солнца не рисуются. Нет плавного смешивания границ каскадов, возможны переходы качества и shadow acne; динамическая оптимизация и caching пока отсутствуют.
- Точечные кубические карты глубины **не поддерживают полупрозрачные BLEND-тени** и используют alpha-test только для MASK. Невозможны мягкие физически точные тени от площади источника.
- Производительность различается по драйверам. Тесты запускаются в Linux через программный OpenGL, визуальное сравнение пока не эталонное.
